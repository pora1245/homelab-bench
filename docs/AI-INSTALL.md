# AI 설치 안내서

이 문서는 Homelab Bench 설치를 요청받은 AI가 사용자의 선택에 맞춰 설치·연결 설정·상태 확인을 진행하는 순서다. 먼저 사용자의 최신 요청과 작업 환경의 지침을 따른다. 설치를 요청받았을 때 수행하며, 이 문서를 읽었다는 이유만으로 설치나 시험을 시작하지 않는다.

## 1. 시작 안내와 질문

다음 내용을 먼저 한국어로 안내한다.

> 이 프로그램은 로컬에서 실행됩니다. 시험 기록과 결과는 설치한 기기에 저장되며 개발자 서버로 자동 업로드되지 않습니다. 벤치 문제는 사용자가 연결한 모델 API로 전송됩니다. 외부 API를 선택하면 해당 제공업체로 전달되며, 채점용 외부 API를 선택한 경우에는 채점에 필요한 문제·정답·모델 답변도 전송됩니다. 설치에 필요한 패키지는 인터넷에서 다운로드합니다.

그다음 아래 세 가지를 한 번에 묻는다. 이미 사용자가 답한 항목은 다시 묻지 않고 반영한다. 답하지 않은 선택을 AI가 임의로 설치 동의로 간주하지 않는다.

1. **시험할 모델은 이 PC에서 실행하나요, 외부 서버에서 실행하나요?** 선택: 이 PC / 외부 서버. 클라우드 모델 API도 외부에 해당한다. ‘이 PC’는 브라우저가 아니라 벤치 실행기를 설치할 기기다.
2. **장비 사용률·온도·전력을 기록할 장비 수집기를 설치하시겠습니까?** 선택: 예 / 아니요. 같은 PC면 앱의 내장 수집을 사용하고, 외부 서버면 모델 서버에 해당 OS용 수집기를 설치한다. 하드웨어에 접근할 수 없는 클라우드 API는 수집하지 않는다.
3. **코딩 문제를 채점할 코드 채점기를 설치하시겠습니까?** 선택: 예 / 아니요. 선택하면 Python 채점 의존성과 Docker Linux 실행 환경이 필요하다. Docker 준비가 필요하면 설치할 구성과 직접 조작해야 하는 단계를 설명한다.

질문 후에는 답변을 요약하고 해당 구성으로 진행한다. 모델 API 주소·모델 ID·API 방식과 외부 서버 접근 방법은 필요한 경우에만 추가로 확인한다. 설치 선택을 앱 화면에서 다시 묻게 하지 않는다.

## 2. 대상 환경 확인

- 벤치 앱을 설치할 기기의 OS·CPU 아키텍처·설치 폴더·사용 가능한 포트를 확인한다. 기본 앱 주소는 `http://127.0.0.1:18760`이다.
- 같은 PC/외부 서버 여부는 사용자의 답변으로 결정한다. API 주소가 localhost라는 이유로 모델의 물리적 위치를 추측하지 않는다.
- GitHub 소스인지 OS에 맞는 실행 번들인지 확인한다. **Code → Download ZIP은 소스이며 실행 파일을 포함하지 않는다.** 소스에는 Rust/Cargo, Node/npm과 해당 Rust 대상의 C/C++ 빌드 도구가 필요하다.
- 실행 파일이 있으면 OS·아키텍처가 일치하는지 확인하고 불필요한 빌드를 하지 않는다. Mac용 실행 파일을 Windows·Linux에 복사해 실행하지 않는다.
- Apple Silicon Mac과 Windows x86_64 실행 ZIP은 기존 기기의 별도 폴더·빈 데이터에서 시작기·화면·기본팩 네 모드를 검증했다. 별도 새 OS·일반 채점 의존성 신규 설치·Linux·Intel Mac 전체 앱은 미검증이다. 실행 ZIP의 작성과 GitHub Release 게시를 구분하고 제공 파일이 실제 있는지 확인한다.
- 설치 의존성은 공식 배포 경로를 사용한다. 인증·관리자 설치·보안 확인처럼 사용자가 직접 처리해야 하는 단계는 구체적인 화면과 이유를 알려준다. 사용자·시스템 전역 설정을 임의로 약화하지 않는다.

## 3. 앱과 선택 구성 준비

### 앱

명령은 저장소 루트에서 실행한다. 다운로드한 실행 번들은 루트에 시작 스크립트가 있고, GitHub 소스에는 `packaging/`에 있다.

| 환경 | 준비와 실행 |
|---|---|
| Apple Silicon Mac 소스 | [README 소스 빌드](../README.md#소스에서-빌드하기)의 `npm ci` → 웹 빌드 → `cargo build --release --locked` → `bin/` 배치 후 Mac 시작 스크립트 |
| Windows 소스 | `powershell -NoProfile -File .\packaging\Build-Source-Windows.ps1` 후 `packaging\Start-Homelab-Bench-Windows.cmd` |
| OS가 맞는 실행 번들 | 동봉된 시작 스크립트로 앱 실행. Rust·Node 빌드 생략 |
| Linux·Intel Mac 전체 앱 | 실행 번들을 제공한다고 가정하지 않는다. 소스 빌드·시작 경로를 별도로 확인하고 미검증 범위를 설명한다. Mac 전용 시작 스크립트는 사용하지 않는다. |

일반 채점 준비는 Mac의 `packaging/Setup-Graders.command`, Windows의 `packaging/Setup-Graders-Windows.ps1`을 사용한다. 시작 스크립트도 첫 실행에 일반 채점 환경을 준비한다. Python 자체가 없으면 현재 스크립트는 공식 설치 화면을 안내하며 설치 완료 후 다시 확인한다. Python을 준비할 수 없다면 실패를 숨기지 말고 내장 채점 과목 사용 가능 여부를 알려준다.

- Python 없이 사용 가능한 기본팩 과목: GSM8K, MMLU-Pro, BBH.
- Python 채점 환경이 필요한 과목: IFEval, MATH-500 및 코드 과목.
- 코드 채점 준비를 선택한 경우에만 아래 Docker 준비를 진행한다.

### 코드 채점기를 선택한 경우

벤치 앱이 실행되는 기기에서 Docker Linux 실행 환경을 확인한다. 모델 서버 위치와 코드 채점기 설치 위치를 혼동하지 않는다.

| OS | 코드 채점 이미지 준비 |
|---|---|
| Windows | `powershell -NoProfile -File .\packaging\Setup-Code-Grader-Windows.ps1` |
| Mac | `zsh packaging/Setup-Code-Grader.command` |
| Linux | `bash packaging/Setup-Code-Grader-Linux.sh` |

준비 스크립트는 코드 실행 이미지를 만들며 Docker 자체나 가상머신을 자동 설치하지 않는다. Docker가 없다면 공식 설치와 필요한 사용자 조작을 안내한 뒤 준비를 재개한다. 생성된 코드를 호스트에서 직접 실행해 채점하는 방식으로 대체하지 않는다. OS 네이티브 샌드박스는 검증 단계이며 현재 지원 경로처럼 안내하지 않는다.

### 장비 수집기를 선택한 경우

- **같은 PC:** 앱 내장 장비 수집을 사용한다. `/api/devices`에서 `mode=local`인 장비를 확인하고 모델 연결의 `device_id`에 지정한다. 별도 수집기 프로세스는 필요 없다.
- **외부 서버:** 모델 서버의 OS·CPU에 맞는 `llm-bench` 실행 파일과 수집기 시작 파일을 준비한다. 수집기 자체는 Python·Docker·평가팩이 필요 없다. 소스에서 실행 파일을 만드는 경우에는 해당 대상의 빌드 환경이 별도로 필요하다.
- **선택하지 않은 경우:** 모델 연결 저장 시 `device_id:""`로 설정한다. API로 새 시험을 만드는 경우에는 최상위 `device_id:null`을 명시해 수집을 끈다. 연결에 장비 ID를 남겨 둔 채 설치 선호만 끄면 명시된 장비 연결이 우선할 수 있다. 다른 장비를 대신 수집하지 않는다.

외부 수집기는 [장비 수집기 안내](DEVICE-COLLECTOR.md)를 따른다. 사용자 답변으로 확인한 서버의 실제 LAN·암호화된 개인 네트워크 IP와 포트를 사용한다. 설정 스크립트에 `--bind` 또는 `-Bind`를 전달해 이미 확인한 주소를 다시 묻지 않도록 한다. Windows에서는 대화형 `.cmd` 대신 `.ps1`에 인자를 전달할 수 있다.

수집기 토큰은 준비 스크립트가 전용 파일로 생성한다. 앱 PC에서 접근할 수 있는 `/metrics` 주소와 토큰을 장비 연결에 저장한다. 연결 파일의 `127.0.0.1`은 해당 서버 자신을 뜻하므로 외부 앱의 주소로 그대로 등록하지 않는다. 자세한 권한·토큰 위치는 장비 수집기 안내를 따른다.

## 4. 앱 시작과 설치 선택 저장

시작 스크립트를 실행하고 `GET /api/health`가 성공할 때까지 확인한다. 장기 실행 프로세스를 도구의 짧은 timeout으로 종료하지 않도록 실행 세션을 유지한다. 앱과 수집기의 실행 방법·중지 방법을 사용자에게 남긴다. 자동 시작 서비스 등록은 별도 요청이 있을 때 진행한다.

앱이 실행되면 사용자의 세 가지 답변을 저장한다. 다음은 **같은 PC + 장비 수집 사용 + 코드 채점 미사용**이라는 답변을 받은 경우의 예다. 실제 답변에 맞춰 값을 바꾼다.

```bash
python3 tools/configure_install.py --api-url http://127.0.0.1:18760 --model-location local --device-collection yes --code-grading no
```

Windows에서는 사용 가능한 Python 3 명령(`py -3` 등)으로 실행한다. `local|remote`, `yes|no` 값을 정확히 지정한다. 도구가 성공했다고 의존성 설치나 연결까지 완료됐다고 판단하지 않는다. 이 도구는 선택만 저장하며 설치·모델 호출을 하지 않는다.

Python 도구를 사용할 수 없는 경우 [API 계약](../API.md)에 따라 같은 로컬 실행기의 `POST /api/setup`을 호출한다. 본문은 사용자 답변을 담은 `schema_version:1`, `model_location`, `device_collection`, `code_grading`, `completed:true`다. 이 저장 위치의 파일명은 호환을 위한 `onboarding.json`이며 앱에 처음 사용 준비 화면을 띄우지 않는다.

## 5. API·장비 연결 설정

AI는 앱의 REST API 또는 연결 관리 화면으로 설정할 수 있다. REST 요청은 벤치 앱과 같은 기기의 loopback 주소로 보내고, 원격 설치라면 해당 기기에서 요청하거나 승인된 터널을 사용한다. 앱을 인터넷에 노출할 필요는 없다.

### 비밀값 처리

API 키·장비 토큰을 일반 채팅에 보내 달라고 하지 않는다. 사용자가 연결 관리의 비밀 입력란에 직접 입력하거나, 사용자가 지정한 기기의 보호된 파일을 읽어 요청 메모리에만 담는다. 비밀값을 명령행 인자·콘솔·로그·스크린샷·보고서·Git 파일에 기록하지 않는다. 다른 기기로 비밀 파일을 옮겨야 한다면 사용자에게 목적과 대상을 먼저 설명하고 허용된 방법으로 처리한다. 키 값 대신 연결 성공 여부만 확인한다.

### 장비 등록

1. `GET /api/devices`에서 장비 목록을 확인한다.
2. 같은 PC 수집을 선택했다면 `mode=local`의 ID를 사용한다.
3. 외부 수집기라면 `POST /api/devices`에 `name`, `mode:"http"`, 실제 `/metrics` 주소인 `url`, 선택한 `gpu_indices`, `include_offload`와 `api_key`에 수집기 토큰을 전달한다. 키는 응답에 나오지 않는다.
4. `POST /api/devices/{id}/check`의 `ok`, `status`, 최신 시각, CPU/RAM/GPU 자료를 확인한다. 전력·온도처럼 해당 OS/장비가 지원하지 않는 값은 누락 사유로 남기고 0으로 채우지 않는다.

### 모델 등록

1. 사용자에게 받은 API 주소·모델 ID·방식을 확인한다. 기본 평가팩에는 별도 채점 모델이 필수가 아니다.
2. `POST /api/connections`로 시험 모델 프로필을 저장한다. 필수 값은 `name`, `kind:"target"`, `base_url`, `model`이다. API 방식은 `api_format:"chat_completions"` 또는 `"responses"`다. 장비 수집을 선택했을 때만 확인한 `device_id`를 연결한다.
3. `defaults`를 지정할 때는 `temperature`, `max_tokens`, `concurrency`, `timeout_s`, `reasoning_effort`를 전달한다. 모델이 지원하는 문맥·출력·추론 설정을 확인하고 임의로 최대값을 쓰지 않는다.
4. 기존 연결을 수정할 때는 조회한 `id`를 사용한다. `api_key` 생략은 키 유지이며 빈 문자열은 삭제라는 차이를 지킨다.
5. `POST /api/connections/{id}/check`에서 모델 목록과 선택한 ID를 확인한다. 이 검사는 `/models` 조회이며 실제 생성 성능을 검증한 것은 아니다. 목록 API가 없는 서비스라면 실패 이유를 기록하고 생성 검증 여부를 별도로 안내한다.
6. 사용자 평가팩에서 LLM 채점이 필요하고 사용자가 선택한 경우에만 `kind:"judge"` 연결을 추가한다. 채점용 API에는 문제·정답·답변과 평가 기준이 전송된다.

전체 본문과 응답 형태는 [API.md](../API.md)를 따른다. 설정 파일이나 SQLite를 직접 편집해 API의 검증을 우회하지 않는다.

## 6. 완료 확인과 사용자 안내

설치가 끝났다고 보고하기 전에 다음을 확인한다.

- 앱 `/api/health` 성공, 홈 접근 가능, 처음 사용 준비 대화창 없음.
- `GET /api/setup`의 저장값이 사용자 답변과 일치.
- 선택한 시험 모델의 연결 확인 결과와 정확한 모델 ID.
- 장비 수집을 선택한 경우 실제 모델 장비에서 최신 자료 수신. 미선택이면 모델 연결의 `device_id`가 빈 문자열이고, API로 생성하는 시험에는 `device_id:null`을 명시함.
- `GET /api/readiness` 또는 선택 과목으로 제한한 `GET /api/readiness?scorers=...`에서 실제 채점 준비 상태 확인. 코드 미선택이면 코드 채점 미준비를 전체 설치 실패로 처리하지 않음.
- 준비되지 않은 항목·직접 조작이 필요한 항목·미검증 환경을 구분해 설명. 사용자의 시험 기록이나 점수 기준을 변경하지 않음.

마지막에는 **앱 주소, 시작·종료 방법, 설치한 구성, 모델·장비 연결 결과, 남은 준비 항목**을 짧게 전달한다. 사용자는 앱의 홈에서 새 시험을 시작하거나 결과를 확인하고, 연결 관리에서 설정·구성 요소를 변경할 수 있다.

설치 확인은 시험 전체 실행과 다르다. 사용자가 벤치 실행을 요청했다면 **기본 벤치팩 → 10분·1시간·4시간·8시간** 중 요청한 모드로 진행한다. 전체 과목 기준41·160·536·1,010문항이며, 실제 값은 `GET /api/packs`의 `basic-bench-v2`와 `sources.modes`에서 확인한다. API 본문은 [새 시험 예제](../API.md#새-시험)를 사용한다. 과목을 제외하면 해당 모드 전체보다 짧아지며 시간 기준도 달라진다.

기본팩과 필요한 원본 자료는 저장소와 실행 번들에 포함돼 있다. 새 설치에는 과거 팩 정의·생성 도구가 없으며, 데이터를 다시 받거나 팩을 재생성하지 않는다. 설치만 요청했다면 모델에 문제를 자동 전송하지 않는다.
