# LLM Bench · 로컬 모델 벤치마크

## 시간별 시험

새 시험에서 **10분(54문항) · 1시간(259문항) · 4시간(995문항) · 8시간(1,959문항)**을 선택할 수 있습니다. 기존 공개 벤치 7종의 고정 발췌이며 작은 팩의 문항은 큰 팩에도 포함됩니다. 단일 요청에서 추론 포함 생성 60 tok/s 기준의 시간 예산으로, 실제 시간 제한이나 완료 보장은 아닙니다. [구성·추론 설정·사용법](docs/TIMED-PACKS.md)을 참고하세요.


모델이 문제를 푸는 과정을 보면서 **답변 품질, 응답 속도, 실행 장비 상태**를 함께 확인하는 로컬 앱입니다. 시험이 끝나면 홈에서 지능·성능·종합 점수를 보고, 보고서를 이미지나 PDF로 저장할 수 있습니다.

벤치 앱과 모델은 **같은 PC에 있어도 되고, 서로 다른 장비에 있어도 됩니다.** 모델은 이미 실행 중인 API에 연결합니다. 앱이 모델을 설치하거나 자동으로 구동하지는 않습니다. 시험 기록은 벤치 앱을 실행하는 장비에 저장됩니다.

**이 프로그램은 로컬에서 실행됩니다.** 시험 기록과 결과는 설치한 기기에 저장되며 개발자 서버로 자동 업로드되지 않습니다. 벤치 문제는 사용자가 연결한 모델 API로 전송됩니다. 외부 API를 선택하면 해당 제공업체로 전달되며, 채점용 외부 API를 선택한 경우에는 채점에 필요한 문제·정답·모델 답변도 전송됩니다. 설치 의존성을 준비할 때는 패키지 다운로드를 위해 인터넷을 사용합니다.

이 저장소는 비공개 베타입니다. 기본 접속 주소는 <http://127.0.0.1:18760>입니다.

## AI에게 설치 요청하기

사용하는 AI에 이 저장소를 읽고 설치해 달라고 요청하세요. AI용 순서와 확인 기준은 **[AI 설치 안내서](docs/AI-INSTALL.md)**에 있습니다.

> 이 저장소의 `docs/AI-INSTALL.md`를 읽고 설치해줘. 모델 실행 위치, 장비 수집기와 코드 채점기 사용 여부를 먼저 물어보고, 내 선택에 맞춰 설치·연결 설정·상태 확인까지 진행해줘.

AI는 다음 세 가지를 질문합니다.

1. **시험할 모델은 이 PC에서 실행하나요, 외부 서버에서 실행하나요?** 클라우드 모델 API도 외부에 해당합니다.
2. **장비 사용률·온도·전력을 기록할 장비 수집기를 설치하시겠습니까?** 같은 PC는 내장 수집을 활성화하고, 외부 서버는 그 서버에 별도 수집기를 설치합니다.
3. **코딩 문제를 채점할 코드 채점기를 설치하시겠습니까?** 선택하면 필요한 Python 채점 환경과 Docker 실행 환경을 안내하고 준비합니다.

답변 후 AI가 운영체제에 맞춰 다운로드·빌드·일반 채점 의존성 준비·앱 시작을 진행하고, 모델 API 및 선택한 장비 연결을 설정합니다. 실제 연결과 채점 준비 상태를 확인한 뒤 결과를 알려줍니다. Python·Docker 설치 화면이나 인증처럼 직접 조작해야 하는 단계는 AI가 해당 단계에서 안내합니다.

앱을 열면 **홈으로 바로 이동**합니다. 설치 때 답한 질문을 앱에서 다시 묻지 않습니다. 모델 연결이 없으면 **연결 관리**로 안내하며, 나중에 모델·장비를 바꾸거나 구성 요소를 추가할 때도 연결 관리를 사용합니다.

## 직접 설치하는 순서

1. **다운로드·압축 해제** — 실행 번들이 있으면 운영체제에 맞는 파일을 받고 폴더 전체를 풉니다. GitHub의 **Code → Download ZIP**은 소스이므로 아래 [소스 빌드](#소스에서-빌드하기)가 먼저 필요합니다.
2. **의존성 준비** — 일반 채점 의존성을 준비합니다. 시작 스크립트도 첫 실행에 이 단계를 자동으로 수행합니다. Python 자체가 없으면 설치 안내에 따라 설치한 뒤 다시 실행합니다.
3. **앱 시작** — 시작 스크립트를 실행하면 브라우저의 홈이 열립니다.
4. **모델·장비 연결** — 연결 관리에서 모델 API를 저장합니다. 코드 채점과 장비 수집은 필요한 구성만 준비합니다.
5. **새 시험** — 평가팩과 빠른/전체 시험을 선택하고 시작합니다.
6. **결과 확인** — 홈의 점수와 시험 현황을 확인하고 보고서 양식을 골라 저장합니다.

### 운영체제별 실행 파일

| 환경 | 일반 채점 최초 준비 | 앱 시작 |
|---|---|---|
| Apple Silicon Mac 실행 번들 | `Setup-Graders.command` | `Start-LLM-Bench.command` |
| Windows 실행 파일을 갖춘 폴더 | `packaging/Setup-Graders-Windows.cmd` | `packaging/Start-LLM-Bench-Windows.cmd` |
| GitHub 소스 | 아래 소스 빌드 후 운영체제에 맞는 준비 스크립트 사용 | 빌드 후 `packaging/`의 시작 스크립트 사용 |

Mac 실행 번들은 Rust·Node 없이 앱을 열 수 있습니다. Windows는 실제 PC에서 앱·채점·시험 실행을 확인했지만, 모든 신규 Windows 환경에서 바로 설치되는 범용 설치 패키지 검증까지 끝난 상태는 아닙니다. 현재 제공 파일은 해당 배포의 첨부 목록을 확인하세요. Intel Mac·Linux 전체 앱의 신규 설치와 macOS 서명·공증은 아직 검증 완료가 아닙니다.

시작한 터미널은 열어 두세요. **브라우저를 닫아도 시험은 계속됩니다.** 시험을 일시정지하거나 완료한 뒤 시작 터미널에서 `Ctrl+C`를 누르면 앱이 종료됩니다.

## 1. 모델과 장비 연결

### 모델이 실행되는 위치

설치 AI가 확인한 위치에 맞춰 연결합니다. 직접 설정할 때는 아래 표를 따릅니다. 여기서 ‘이 PC’는 브라우저를 연 기기가 아니라 **벤치 앱 실행기가 설치된 장비**입니다. 연결은 **연결 관리**에서 추가하거나 변경할 수 있습니다.

| 선택 | 설정할 내용 |
|---|---|
| **벤치 앱과 같은 PC** | 모델 API를 등록하고, 장비 수집은 내장 수집을 사용합니다. 별도 수집기를 띄울 필요가 없습니다. |
| **다른 PC·서버** | 해당 모델 서버의 API 주소를 등록합니다. 하드웨어 상태도 보려면 **모델 서버에** 장비 수집기를 설치합니다. |
| **클라우드 API** | API 주소·키·모델 ID를 등록합니다. 서버에 수집기를 설치할 수 없다면 장비 수집을 끄고 시험할 수 있습니다. |

### 모델 API 저장

**연결 관리 → 모델 추가**에서 다음 값을 입력합니다.

| 항목 | 입력 예·설명 |
|---|---|
| 이름 | 목록에서 알아보기 쉬운 이름 |
| API 주소 | 같은 PC라면 예: `http://127.0.0.1:8000/v1`, 외부 서버라면 그 서버의 실제 주소 |
| API 방식 | 서버가 제공하는 **Chat Completions** 또는 **Responses** |
| 모델 ID | API 서버에 등록된 정확한 모델 이름 |
| API 키 | 인증이 필요한 서버에만 입력 |
| 실행 기본값 | 출력 토큰 한도, 동시 요청 수, Temperature·추론 설정 등 |
| 실행 장비 | 실제 모델이 돌아가는 장비를 지정; 게이트웨이 주소만 보고 자동 추정하지 않음 |

저장 후 **연결 확인**을 누릅니다. 연결과 기본값은 다음 시험에서도 재사용하므로 평가팩을 바꿀 때마다 다시 입력할 필요가 없습니다. 외부 API를 시험하면 해당 제공자의 요금·토큰 사용량이 발생할 수 있습니다.

**시험 모델**이 답안을 생성합니다. **채점 모델** 연결은 LLM 판정이 필요한 사용자 평가팩 등에 사용하는 별도 선택 항목입니다. 기본 평가팩은 각 팩의 정답·규칙·공식 채점기를 사용하므로 채점용 API를 반드시 연결할 필요는 없습니다.

### 장비 수집기 연결

외부 서버의 사용률·온도·전력을 보려면 모델 서버의 OS와 CPU에 맞는 수집기를 준비합니다. **장비 수집기에는 Python·Docker가 필요 없습니다.**

| OS | 준비 | 시작 |
|---|---|---|
| Windows | `Setup-Device-Collector-Windows.cmd` | `Start-Device-Collector-Windows.cmd` |
| Mac | `Setup-Device-Collector.command` | `Start-Device-Collector.command` |
| Linux | `bash Setup-Device-Collector-Linux.sh` | `bash Start-Device-Collector-Linux.sh` |

수집기 전용 번들에서는 루트, 전체 소스 폴더에서는 `packaging/`에 있습니다. 서버의 실제 LAN·Tailscale 주소를 지정해 실행한 뒤, **연결 관리 → 장비 추가**에 `collector-connection.json`의 주소와 `agent-token.txt`의 인증 키를 입력합니다. 이 키는 모델 API 키와 다릅니다. 장비 연결을 확인하고 모델의 실행 장비로 선택합니다. 설정 명령과 토큰 파일 위치는 [장비 수집기 안내](docs/DEVICE-COLLECTOR.md)를 참고하세요.

장비 연결이 없어도 모델 API 시험은 할 수 있습니다. 수집할 수 없는 값은 0으로 채우지 않고 **미수집**으로 표시합니다.

## 2. 채점 환경 준비

코드 채점과 장비 수집은 독립적인 선택 기능입니다. 설치 AI가 답변에 따라 준비하고 실제 상태를 확인합니다. 추후 추가할 때는 **연결 관리**에서 준비 방법과 상태 확인을 사용할 수 있습니다.

| 평가 영역 | 필요한 환경 |
|---|---|
| GSM8K·MMLU-Pro·BBH·API Experience | 앱 내장 채점기. Python·Docker 없이 사용 가능 |
| MATH-500·IFEval | Python 3.11 이상과 일반 채점 의존성. IFEval은 NLTK 자료도 필요 |
| HumanEval·MBPP·별도 설치한 LiveCodeBench | 일반 채점 환경과 실행 중인 Docker Linux 컨테이너 환경 |
| 장비 상태 수집 | 내장 수집 또는 별도 Rust 수집기. Python·Docker 불필요 |

일반 채점 준비 스크립트는 `.venv`와 필요한 의존성을 준비하고 이미 준비된 환경은 재사용합니다. Python 자체가 없다면 공식 설치 페이지를 안내하며 설치 화면은 사용자가 진행합니다. 일반 준비에 실패해도 내장 채점기로 가능한 과목부터 사용할 수 있습니다.

**Docker는 코드 시험을 할 때만 필요합니다.** Docker 환경을 설치·실행한 뒤 아래 스크립트로 코드 채점 이미지를 준비하고 앱에서 상태를 확인하세요.

- Windows: `packaging/Setup-Code-Grader-Windows.cmd`
- Mac 실행 번들: `Setup-Code-Grader.command` — 소스 폴더에서는 `packaging/` 안에 있습니다.
- Linux: `bash packaging/Setup-Code-Grader-Linux.sh`

준비 스크립트가 Docker나 가상머신을 자동 설치하지는 않습니다. 현재 코딩 답안은 네트워크·호스트 마운트 없이 읽기 전용 컨테이너에서 비root 사용자와 CPU/RAM/PID 제한으로 실행합니다. Windows AppContainer·Mac App Sandbox를 사용하는 방식은 아직 검증 단계입니다.

## 3. 시험 실행과 실시간 확인

1. **새 시험**에서 저장한 모델을 고릅니다.
2. 종합 또는 개별 **평가팩**을 고르고 **빠른 시험 / 전체 시험**과 과목을 선택합니다. 빠른 시험은 고정된 대표 문항을, 전체 시험은 해당 팩의 전체 평가 구간을 사용합니다.
3. 화면의 선택 문항 수와 실행 설정을 확인합니다. 지능·성능·종합을 함께 보려면 **API 사용성 영역을 포함한 종합 시험**을 선택하세요. 성능 기준 비교는 동시 요청 1개 설정을 사용합니다.
4. **채점 준비 완료**를 확인하고 시작합니다. **준비 필요**는 누락 환경, **확인 실패**는 상태 확인 오류입니다. 안내대로 준비한 뒤 **상태 다시 확인**을 누릅니다.
5. **시험 현황**에서 문제, 모델 답안, 정답·채점 기준, 문항별 정답/오답을 확인합니다. 문항별 판정은 접을 수 있고, **진행 따라가기**를 끄면 이전 문항을 볼 수 있습니다.
6. 필요하면 **일시정지**하거나 **중단**합니다. 원격 모델 서버가 이미 받은 요청을 즉시 멈출 수 있는지는 해당 API 구현에 따라 다릅니다.

동시작업은 **자동 선택**이 기본입니다. 과목과 길이를 나눠 고른 같은 문항을 단일·동시 요청으로 최대 10분 동안 비교합니다. 기존 설정과 상한 내 후보를 각각 3회 확인하며, 중간 설정이 느려도 더 높은 후보를 생략하지 않습니다. 앱 저장·채점 대기와 모델 API 처리시간을 분리하고, 근거가 부족하면 기존 설정을 유지합니다(새 시험은 단일). 변경 뒤 비교 가능한 본시험 처리량이 악화되면 진행 중 응답을 끝낸 뒤 이전 설정으로 복구합니다. 직접 지정한 동시 수는 자동 변경하지 않습니다.

시험 중 TTFT·Decode·Prefill·Throughput과 연결된 장비 상태가 함께 기록됩니다. 시험이 끝나면 **같은 실행에서 점수를 자동 산출합니다.** 성능 점수를 받기 위해 따로 재계산 버튼을 누르거나 같은 시험을 다시 돌릴 필요는 없습니다.

## 4. 점수와 보고서 읽기

홈에서 시험 기록을 선택하면 **그 기록의 점수와 결론**을 보여줍니다.

| 점수 | 의미 |
|---|---|
| **지능 /100** | 고정 평가 영역의 답안 품질을 합성한 점수 |
| **성능 · 상한 없음** | **GPT-6.1 Sol Low API 실측 = 1,000점**으로 둔 응답 경험 지수 |
| **종합 /100** | 지능 70%·기준 대비 성능 30%의 기하평균. 기준 이상의 성능은 종합 계산에서 만점으로 처리 |

성능은 **단일 요청의 가시 Decode·TTFT 기본점수 + 같은 표본으로 검증한 동시 처리 가산점**입니다. 기존 단일 측정 이력도 사용하므로 동시작업으로 전환해도 기본점수가 떨어지지 않습니다. 통신·서비스 대기·추론을 포함한 실제 API 사용 경험이므로 순수 GPU 연산 성능 순위와는 다릅니다. Prefill은 서버가 제공한 경우만 표시합니다.

**범위**는 평가하지 않은 지능 영역이 남아 있다는 뜻이고, **미산출**은 필요한 자료가 없다는 뜻입니다. 미측정 값을 임의로 채우지 않습니다. 기본 번들에 없는 LiveCodeBench 때문에 지능·종합이 범위로 표시될 수 있습니다. 빈 응답·요청 오류·출력 잘림은 정상 성능 표본으로 사용하지 않습니다. 완료된 코드 블록의 형식 준수 여부는 성능 유효성과 분리하여 진단합니다. 이전 판정 버전의 성능 기록은 앱 시작·가져오기·휴지통 복원 시 자동 반영합니다.

앱의 합성 점수는 공식 벤치마크 리더보드 점수가 아닙니다. 세부 산식·비교 조건은 [점수 정책](SCORE-POLICY.md)에서 확인할 수 있습니다.

1. 기록을 선택하고 **보고서**를 엽니다.
2. **보고서 양식**에서 종합·지능·성능·문항별 보고서를 선택합니다.
3. **테마**에서 라이트·다크·인쇄용을 고릅니다. 화면에 보이는 보고서가 저장 대상입니다.
4. **저장** 버튼을 누르고 형식을 선택합니다.

종합 보고서는 점수와 함께 연결된 장비의 사양·실측 사용률·온도·전력·시험 조건을 보여줍니다. 수집하지 못한 장비 정보는 미수집으로 남습니다. 도움말은 데스크톱의 마우스 올리기·클릭·키보드 초점과 모바일 탭으로 볼 수 있습니다. 시험 이력은 **시험 기록 관리**에서 휴지통으로 옮기고 복원할 수 있습니다.

## 포함된 평가팩

| 평가 용도 · 팩 | 전체 | 빠른 | 기본 배포 |
|---|---:|---:|---|
| 수학 추론 · GSM8K | 1,319 | 50 | 포함 |
| 고난도 수학 · MATH-500 | 500 | 50 | 포함 |
| 지식·추론 · MMLU-Pro | 12,032 | 100 | 포함 |
| 지시 이행 · IFEval | 541 | 50 | 포함 |
| 함수 구현 · HumanEval | 164 | 25 | 포함 |
| 기초 프로그래밍 · MBPP | 500 | 25 | 포함 |
| 알고리즘 · LiveCodeBench v6 | 1,055 | 30 | 로컬 별도 설치 |
| 복합 논리 추론 · BIG-Bench Hard | 6,511 | 54 | 포함 · 별도 확장 정확도 |
| 기본 번들 종합 | **21,567** | **354** | 7개 품질팩 |
| LiveCodeBench까지 설치 시 | **22,622** | **384** | 로컬 추가 설치 |

새 종합 시험은 공개 품질 팩 7종으로 구성한다. 기존 범위에 MATH-500·MMLU-Pro를 포함하고 복합 논리 추론을 보는 BBH 전체 평가 자료를 추가했다. BBH는 공식 3-shot CoT 예시와 문항별 정답 일치로 채점하며, 논문의 과제별 평균과 구분한다. 원본에 잘린 문항1개·상충 정답4개가 있어 이를 표시하고 0점이 아닌 채점 제외로 남긴다(전체 최대6,506문항 채점). 홈·보고서에 별도 정확도로 표시하고 기존 지능·종합 지수의 가중치는 유지한다. LiveCodeBench는 문제·테스트 자료의 재배포 조건이 미확정이라 별도 설치하며, 미측정 영역이 있으면 지능·종합 점수는 범위로 남는다. 성능은 품질 문제를 푸는 동안 수집한 응답 시간과 생성 속도로 계산한다. 기존 API Experience 자료는 과거 기록·기준값·API 호환용으로 보관하고 새 시험 선택에서는 숨긴다. 자체 한국어와 예전 100문항 팩은 신규 선택·배포에서 제외하고 과거 기록만 보존한다.

원본·설치·선택 문항 수와 고정 리비전·입력 해시를 기록한다. [데이터 설치](datasets/README.md), [제3자 고지](docs/THIRD-PARTY-NOTICES.md), [배포 범위 감사](docs/DISTRIBUTION-LICENSE-AUDIT.md)를 따른다. 데이터별 조건이 불명확한 자료는 배포본에 넣지 않는다. 별도 다운로드는 이용자가 해당 자료 조건을 확인해 선택한다.

## 채점 방식과 측정 기준

GSM8K는 숫자 추출, MATH는 Math-Verify 0.9.0, MMLU-Pro는 5-shot·선택지 추출을 사용합니다. IFEval은 공식 strict를 주 점수로 쓰고 loose·개별 지시 결과도 보존합니다. HumanEval·MBPP·LiveCodeBench는 원본 테스트와 공식 실행 코드를 격리 Docker에서 사용합니다. BBH는 공식 고정 CoT 프롬프트와 버전 고정 답안 추출기를 사용합니다. 공식 방식과 앱 연결부의 차이는 [데이터 문서](datasets/README.md)에 기록합니다.

- **TTFT:** 요청 시작부터 가시 답변 첫 텍스트까지. 추론 첫 도착 시각은 별도 보관합니다.
- **Decode:** 서버 내부 속도와 클라이언트 가시 출력 속도를 구분합니다. 성능 점수는 후자를 사용하며 숨은 추론 토큰은 제외합니다.
- **성능 점수:** 단일 요청 TTFT·가시 Decode가 기본입니다. 같은 표본의 동시 처리량과 완료시간이 모두 개선된 경우 가산하며 유효 단일 측정 1쌍부터 잠정 표시합니다. 가산율은 이득 2배당 기본의 10%, 최대 30%인 베타 정책입니다. [점수 정책](SCORE-POLICY.md)에 산식과 한계를 기록합니다.
- **Prefill:** 서버가 제공한 값만 표시합니다. API가 제공하지 않으면 미수집입니다.
- **Throughput:** 완료 응답 토큰과 전체 처리 시간으로 계산합니다. 단일 사용자 속도와 동시 요청 처리량을 구분합니다.
- **장비:** 선택 GPU 사양·사용률·온도·보드 전력·클럭·관측 PCIe 링크, 장비 CPU/RAM/swap을 수집합니다. Offload 선택 시 NUMA·스토리지 읽기를 추가합니다. 장비 전체 사용량을 모델 단독 사용량으로, GPU 보드 전력을 서버 전체 전력으로 해석하지 않습니다.

환경 실패·요청 오류·출력 잘림·오답을 구분하며 환경 실패를 오답 0점으로 바꾸지 않습니다. 저장된 답안을 재채점할 때 모델을 다시 호출하지 않으며 이전 채점 이력도 보존합니다.

| 증상 | 확인할 내용 |

| 시작 파일을 눌러도 실행 파일이 없다고 나옴 | GitHub 소스만 받은 경우 아래 빌드가 필요합니다. 실행 번들은 전체 폴더를 압축 해제하세요. |

| 지능·종합이 범위로 나옴 | 미설치·미측정 평가 영역을 확인합니다. 앱 오류와 구분됩니다. |
| PDF 저장 창이 안 열림 | 브라우저의 인쇄 팝업 허용 상태를 확인하고, HTML 또는 PNG·SVG 저장도 사용할 수 있습니다. |

## 기록 위치와 백업

| 실행 방식 | 기본 데이터 폴더 |
|---|---|
| Mac 번들·소스 직접 실행 | 앱 폴더의 `data/` |
| Windows 준비·시작 스크립트 | `%LOCALAPPDATA%\LLM-Bench\data` |
| 별도 경로 지정 | `BENCH_DATA_DIR` 또는 Windows 시작 스크립트의 `-DataDirectory` 값 |

기록·연결 설정은 `app.sqlite3`, API 키는 별도 `credentials.json`에 저장됩니다. Unix에서는 데이터 폴더 0700·키 파일 0600으로 제한하지만 OS 키체인은 아닙니다. 키는 일반 조회 응답·시험 원문·보고서에 내보내지 않습니다.

앱을 종료한 뒤 **해당 데이터 폴더 전체를 백업**하세요. 실행 중에는 SQLite backup 방식이 필요하며 DB 파일만 단순 복사하지 않습니다. 업데이트할 때도 데이터 폴더를 보존합니다. AI 설치에서 저장한 구성 선택은 `onboarding.json`, NLTK 자료는 `nltk_data/`에 있습니다. 파일 이름은 이전 버전과 호환되며 별도 초기 준비 화면을 뜻하지 않습니다.

원본 JSON에는 프롬프트·모델 답변·메모·내부 주소 등이 포함될 수 있습니다. 공유 전 내용을 확인하세요. 사용한 앱 폴더를 그대로 올리면 개인 데이터가 섞일 수 있으므로 GitHub에는 개인 `data/`, 키, 실행 기록, 캐시를 업로드하지 않습니다. 앱이 결과를 온라인으로 자동 공유하는 기능은 현재 없습니다.

## 소스에서 빌드하기

이 절은 **GitHub 소스 또는 소스 ZIP**을 받은 경우입니다. 명령은 저장소 루트에서 실행합니다. Rust/Cargo와 Node.js/npm, 선택한 Rust 도구 체인에 맞는 C/C++ 빌드 환경이 필요합니다. 일반 채점에는 Python 3.11 이상, 코드 채점에는 추가로 Docker 환경이 필요합니다.

### Apple Silicon Mac

```bash
cd web
npm ci
npm run build
cd ..
cargo build --release --locked
mkdir -p bin
cp target/release/llm-bench bin/llm-bench
zsh packaging/Setup-Graders.command
zsh packaging/Start-LLM-Bench.command
```

최초 준비를 나중에 하려면 마지막 명령을 `BENCH_SKIP_SETUP=1 zsh packaging/Start-LLM-Bench.command`로 실행할 수 있습니다. Python 경로를 직접 지정하려면 준비 명령 앞에 `BENCH_SETUP_PYTHON=/실제/Python/경로`를 설정합니다.

### Windows PowerShell

```powershell
Set-Location web
npm ci
npm run build
Set-Location ..
cargo build --release --locked
New-Item -ItemType Directory -Force bin
Copy-Item target\release\llm-bench.exe bin\llm-bench.exe -Force
.\packaging\Setup-Graders-Windows.cmd
.\packaging\Start-LLM-Bench-Windows.cmd
```

준비를 건너뛰고 내장 과목부터 실행하려면 `.\packaging\Start-LLM-Bench-Windows.cmd -SkipSetup`을 사용합니다. 기록 폴더나 포트를 바꾸려면 `-DataDirectory 'D:\LLM-Bench-Data' -Port 18762`처럼 지정합니다. 명령 실행이 실패하면 다음 단계로 진행하기 전에 해당 오류를 해결하세요.

### 개발용 실행과 검사

`BENCH_PORT`, `BENCH_DATA_DIR`, `BENCH_PYTHON`으로 포트·기록 위치·채점 Python을 지정할 수 있습니다. UI 빌드 후 `cargo run --locked`로 개발 실행할 수 있으며 기본 서버는 loopback에만 바인딩합니다.

```bash
cargo test --locked
cargo build --locked
python3 tests/integration.py
python3 tests/experience_contract.py
.venv/bin/python tests/code_scoring_contract.py
.venv/bin/python tests/dataset_contracts.py
.venv/bin/python tests/installer_contracts.py
```

마지막 세 검사는 준비된 채점용 Python을 사용합니다. Windows에서는 `.venv/bin/python` 대신 `.venv\Scripts\python.exe`를 사용하세요. 검사는 임시 DB·모의 API·고정 채점 예제를 사용하며 실제 모델 시험을 새로 실행하지 않습니다.
